title: The reviewer wrote its verdict where nobody looked
slug: 2026-10-12-the-reviewer-wrote-its-verdict-where-nobody-looked
date: 2026-10-12
blog: no
subtitle: A document pipeline had a second model review every draft. Its doubt went into a JSON field on the server while the CRM note said "use this one" — and the better of two letter generators had never run, because the first writer won
concepts: advisory-feedback, single-source-of-truth, silent-failure, verify-from-logs
symptom: The operator asked whether a machine-built CV was strong enough for a specific posting. Three independent readers — a general-purpose chat model, this session, and the pipeline's own second-model reviewer — reached the same verdict, that it covered three of the posting's five duties and lacked the stakeholder and compliance evidence the role was built around. The reviewer had written exactly that into the draft's metadata on the server at build time. The CRM note that the operator reads on her phone carried the file with the line "use this one" and no caveat. The same pipeline's cover-letter generator, which reads a block of verified facts and refuses invented claims, had produced zero letters on this class of deal for weeks; its run log said "already had a letter 10 · wrote 0" every ten minutes, because an upstream job-search bot writes a generic letter first and the kit treated any note containing the words "cover letter" as done.
root_cause: Four generators, one pipeline, no shared evidence. The CV composer chose lines from a reviewed bank; the letter and the interview-defense generator read a hand-typed facts block of eight lines with a single number in it; the question-and-answer picker read a third file. Each copy was true and each was thin, so every output was true and generic. The reviewer's doubt was advisory by construction: computed, stored, never surfaced to the person deciding. And the letter path had a precedence bug — the first note to mention a cover letter blocked the better generator — so a design that explicitly existed to replace a stub never executed on the deals that most needed it.
fix: Nothing new was built. The facts block now loads from the reviewed bank at start, so the letter, the defenses and the CV draw on the same lines, and the hand-typed list is only a fallback when the bank cannot be read. The bank grew by the lines a four-lens review had just passed, each checked in code as a verbatim substring of its source document. Three verified answers were added to the defense bank. The letter step is skipped only when the pipeline's own letter note exists or a hand-written one does, and the letter note now carries the deal's own CV instead of the generic lane file. The composer keeps at most one summary from the current era, picks all the past-role lines when a posting names stakeholders or compliance, and keeps the posting's exact word forms in headings after two of three attempts were lost to "drive" where the posting said "driving". And the reviewer's note is printed on the CRM line next to the file, so a machine draft can no longer say "use this one" while its own reviewer disagrees.
verified: From the pipeline's log and the CRM, not from the deploy. Before: every ten-minute run ended "already had a letter 10 · wrote 0". The first run after the change: "already had a letter 2 · wrote 8", one letter per deal that had only the upstream bot's draft; one of them read back from the CRM is built from the bank's lines with no invented claim. A dry build of the CV composer against the posting that started this produced four headings that are verbatim substrings of the posting, nine bullets including the hallucination-guardrail line, one summary paragraph and all three past-role lines; the first dry build had failed because two of three attempts were spent on re-worded headings. The verbatim check over the bank reported zero misses across 23 bullets, 5 summaries, 9 live lines and 7 role lines. The five changed files are byte-identical on the laptop and the server.
rule: A review that only informs is not a control. If a second model's verdict matters, it must travel with the artifact to the place where the decision is made, or it is a log line nobody reads. And when two writers can produce the same artifact, decide precedence on purpose: "someone already wrote one" is how the worse draft wins forever.
