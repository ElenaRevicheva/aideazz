title: The cut landed inside an emoji

subtitle: A job posting trimmed to 6,000 characters ended halfway through one emoji. Every structured call to the primary model answered 400, and the whole document kit for that deal was quietly built and reviewed by the fallback model instead
concepts: fabrication-under-degradation, verify-from-logs, redundancy-is-not-precedence
symptom: The first job deal processed after a pipeline upgrade got its complete kit on schedule, six minutes after it arrived: company brief, role defense, technical defense with a composed CV, cover letter, browser prompt. The run log also carried four lines that appear nowhere else in the log's history: the primary model's API answering "400 Invalid body: failed to parse JSON value" on the role-defense draft, the role-defense review, the CV composer and the CV reviewer, each followed by "falling back to the quality chain" and a 13,000-character answer from the fallback model. Nothing failed from the operator's point of view. The deal looked complete, and it was, but the CV had been composed and judged by a different model than the design specifies.
root_cause: The posting fetcher trims page text to 6,000 UTF-16 code units. On this posting the 6,000th unit was the first half of a fire emoji. JavaScript's JSON serialiser writes an unpaired half as a bare escape, which is well-formed JSON text but not a valid string value, and the API's parser rejected the entire request body. The letter generator survived because its provider chain tries another model on any error, so the posting passed through a different path. The bank of verified facts that had been added the night before was the obvious suspect and was innocent: a bisect probe sent the posting as fetched (400), the same posting with the lone half removed (200), the fact bank (200) and the defense bank (200). A second defect surfaced on the re-probe: the same fetcher left hexadecimal HTML entities raw and turned decimal ones into spaces, so the text read "organisation&#x27;s" and the composer rejected a heading the model had copied word for word, because the substring check could not find the apostrophe.
fix: Two changes inside the existing functions, nothing new. Fetched text now has every unpaired surrogate half removed, and both request builders strip them again before serialising, so no input can produce a bare escape. The HTML-to-text step decodes hexadecimal and decimal numeric entities, quotes and apostrophes, with the ampersand entity decoded last so a double-encoded value is not decoded twice. Nothing on the affected deal was rewritten; its fallback-built kit stays, and a rebuild on the primary pair is a hand-run option.
verified: From the log and a probe, not from the diff. The error string occurs exactly four times in the kit's log, all within one run. The probe reproduced it on the posting as fetched and cleared it by removing one code unit at index 5,999. After deploy, the composer run on that same posting through the kit's own fetcher reported zero lone surrogates and finished on the primary pair, drafted by one model and reviewed by the stronger one, with three headings that are verbatim substrings of the posting, one of them containing the decoded apostrophe. The compiled module and its source are byte-identical on the laptop and the server.
rule: Truncate text on characters, never on code units, and sanitise at the boundary where text leaves your system, because the parser on the other side does not owe you tolerance. A loud fallback is still a fallback: when a cheaper model silently takes over review as well as drafting, the artifact's quality changed and nothing in the output says so, so grep the run log for the primary model's refusals before trusting a green run.
