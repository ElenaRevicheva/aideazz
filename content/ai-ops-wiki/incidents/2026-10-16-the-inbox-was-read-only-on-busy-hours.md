title: The inbox was read only on busy hours
slug: 2026-10-16-the-inbox-was-read-only-on-busy-hours
date: 2026-10-16
blog: yes
subtitle: An hourly job hunter also reads two mailboxes for employer replies. An hour that found no new jobs ended early, before the mailbox step, so replies were read in 278 of 466 cycles, with gaps of up to 14.4 hours
concepts: fate-sharing, silent-failure, liveness-is-not-correctness, verify-from-logs
symptom: While the bot's help screens were being rewritten, a read-only check compared every sentence with the service's own log, including how often the job-search inboxes were read. Over the 466 hourly cycles in the retained log (27 September to 16 October 2026), the mailbox step started 278 times. The hours that skipped it did not look broken: each logged a calm, true line, "No new jobs this cycle (N consecutive) - waiting for next run", and the service never crashed; its restarts in that period were all clean, deliberate ones.
root_cause: One function runs the whole cycle as numbered steps: find jobs, score and route them, send a summary, send follow-ups and warm introductions, then read the mailboxes for replies. When the search found zero new jobs, the function returned right after saying so. That was correct for the scoring steps, which had nothing to score, but it also skipped the mailbox step, which has nothing to do with whether new jobs exist. Reading replies shared the fate of finding jobs: 187 of the 466 cycles found nothing new, so about four hours in ten never looked at the inbox. A 24-hour look-back in the mailbox scan hid the gap. The longest stretch between two checks was 14.4 hours, fourteen quiet cycles in a row, inside the window, but that was margin, not design: a quiet spell longer than a day would have made replies invisible.
fix: In the zero-jobs branch, the same reply-check block now runs before the early return. Nothing else in the cycle changed, and the existing de-duplication still alerts each email once. Because the check now runs every hour, the reply-check mail connections also got a 60-second timeout, so a hung mail server can block the single event loop the cycle shares with the chat bot and a daily marketing post for about a minute per call instead of indefinitely. The change does not touch the marketing post's code or schedule.
verified: From the service log. Before the fix, over the retained log from 27 September to 16 October 2026: 466 cycles, 187 with zero new jobs, 278 mailbox checks, and a longest gap of 14.4 hours between two checks. An independent fact-check recounted those numbers from the same log and matched them. After the deploy, the first quiet cycle, at 17:55:59 UTC, logged "Found 0 new jobs", then "No new jobs this cycle (1 consecutive) - waiting for next run", then "Checking for responses", and "Response check complete" at 17:56:43: the step a quiet hour used to skip now runs. The cycles that found jobs that afternoon completed the check as before.
rule: Count how often each duty actually runs from its own log line, not how often the loop runs. When one function carries several duties, an early return is a decision about all of them: put a duty that does not depend on the branch before the branch, or give it its own trigger.
