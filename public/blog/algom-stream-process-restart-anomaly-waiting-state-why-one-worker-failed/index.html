algom-stream Process Restart Anomaly Waiting State: Why One Worker Failed

November 24, 2026 · by Elena Revicheva

algom-stream entered the waiting restart state after 29946 restarts while 8 processes supervised by PM2 remained online. The operating table showed a stark contrast: sibling workers like algom-poll held 0 restarts and 10d uptime at 79 MB, yet algom-stream collapsed into a thrashing loop that forced PM2's backoff logic to stall it entirely. This was not a system-wide infrastructure outage; it was an isolated, unbuffered streaming failure occurring on the exact same host.

When seven other background daemons run undisturbed for 10d, an isolated crash loop reveals a flaw in how an application interacts with an external socket or state engine. Here is the operational diagnosis of that failure, how PM2 handles continuous thread crashes, and why algom-stream crashed while sibling workers survived.

The Topology of an Isolated Daemon Crash Loop

Looking at pm2 jlist reveals exactly where the failure is isolated. The host operates 9 supervised processes in total. Exactly 8 are online, and 1 is trapped in a crash cycle:

  • pm2-logrotate: online, 0 restarts, up 10d, 88 MB
  • dragontrade-dashboard: online, 0 restarts, up 10d, 77 MB
  • cto-aipa: online, 25 restarts, up 0d, 238 MB
  • algom-stream: waiting restart, 29946 restarts, up 0d
  • dragontrade-main: online, 0 restarts, up 10d, 184 MB
  • algom-poll: online, 0 restarts, up 10d, 79 MB
  • whitespace: online, 0 restarts, up 10d, 119 MB
  • n8n: online, 0 restarts, up 10d, 424 MB
  • serpapi-jobs: online, 0 restarts, up 10d, 124 MB

The key comparison is between algom-stream and algom-poll. Both target the exact same operational domain. algom-poll has run cleanly for 10d using 79 MB and logged 0 restarts. It issues discrete, scheduled requests, ingests the response, updates state, and disconnects.

algom-stream, however, maintains a persistent ingestion connection. When network instability, connection resets, or unhandled socket drops sever that connection, the process fails if it lacks localized reconnection backoff. Instead of catching an unhandled socket drop internally, the script exits directly to the kernel, throwing the entire restart burden onto PM2. At 29946 restarts, PM2 marks the process as unstable and holds it in the waiting restart state.

Why Sibling Workers Survived 10 Days Without a Restart

The contrast between algom-stream and dragontrade-main (10d, 0 restarts, 184 MB) or dragontrade-dashboard (10d, 0 restarts, 77 MB) shows that host memory exhaustion or CPU starvation was not the culprit. The host has sufficient capacity; even high-footprint services like n8n sit comfortably at 424 MB without crashing.

Processes structured around discrete intervals or stateless request-response architectures naturally isolate external errors. For instance, in our logs for other operations:

  • deal-digest.log records scheduled updates pulling 23 live job deals into markdown files.

  • espaluz-truth.log writes 478 rows to truth_people without tearing down its execution context.

  • atlas-lead-machine.log notes staged 8 · looked at 11 · no-email 0 · already-in-CRM 3 and exits cleanly.

In contrast, streaming processes attempt to hold open-ended execution loops. If the remote endpoint abruptly closes the connection, the socket emits an event that, if left unhandled, crashes the Node.js runtime.

We see this exact pattern in our Python pipelines as well. In model-tier.log, an unbuffered connection triggers:

raise self.abort('socket error: EOF')
imaplib.IMAP4.abort: socket error: EOF
imaplib.IMAP4.abort: command: FETCH => socket error: EOF

When a socket errors with EOF or drops mid-stream, the code must anticipate that termination. If a worker treats a network disconnect as a fatal exception rather than an expected lifecycle event, process supervisors will register tens of thousands of restarts.

Understanding the PM2 Waiting Restart State

PM2 uses restart delay mechanisms (such as exponential backoff) to protect host resources from runaway scripts. When a process crashes repeatedly in seconds, immediate restarts consume CPU cycles, exhaust file descriptors, and bloat log files.

Once PM2 detects that a process cannot maintain an active state for longer than a minimal stability threshold, it throttles the spawn rate:
1. The process exits with an error code or an unhandled exception.
2. PM2 increments the restart counter (hitting 29946 restarts).
3. The supervisor places the process into the waiting restart state, introducing a progressive delay before executing the next fork attempt.
4. If the root cause is environmental or an invalid runtime configuration that crashes instantly on entry, the process spends nearly its entire lifecycle toggling between spawning and waiting restart.

During this time, memory allocation drops to zero or remains unmeasured because the process is not actively running. Meanwhile, sibling processes like cto-aipa show 25 restarts and 238 MB of memory while staying online, proving that a process can recover from intermittent churn if it can hold its operational loop long enough to clear the crash window.

Decoupling Polling from Streaming in Resilient Architectures

The operational stability of algom-poll (0 restarts over 10d) versus algom-stream (29946 restarts) underscores a fundamental production trade-off: streaming provides low latency, but polling provides superior failure isolation.

When building reliable automation, streaming connections require:

  • Explicit error listeners on the underlying socket to prevent unhandled rejections from bubbling to the process supervisor.

  • In-process exponential backoff before attempting to reconstruct the stream.

  • A fallback path that switches to discrete polling if the stream cannot be negotiated within 3 attempts.

If a worker cannot maintain stream continuity, it should fall back to bounded batch queries like algom-poll. Polling handles downstream rate limits and network degradation gracefully. For example, when atlas-outcomes.log encountered API limits:

hs-outcomes-to-atlas fatal: Error: HubSpot 429: {"status":"error","message":"You have reached your secondly limit.","errorType":"RATE_LIMIT","correlationId":"01a20907-4ac0-7bf2-95ab-2063f165d7de","policyName":"SECONDLY","groupName":"publicapi:crm:s

The scheduled script terminated its execution run cleanly upon hitting the HTTP 429 limit. It did not trigger an infinite crash-and-restart cascade; it simply waited for the next scheduled invocation. Persistent streams lack that natural boundary unless deliberately written into the error-handling loop.

Frequently Asked Questions

Q: Why does PM2 show the memory usage of algom-stream as empty or unrecorded?
A: When a process enters the waiting restart state, the operating system process has completely terminated. Because no active PID exists while the process is delayed in backoff, PM2 cannot sample memory usage.

Q: Did the high restart count of algom-stream impact sibling processes on the machine?
A: No. PM2 isolates process contexts, allowing 8 out of 9 processes—including dragontrade-main (184 MB) and n8n (424 MB)—to maintain uninterrupted uptime for 10d.

Q: What is the main structural reason algom-poll stayed online while algom-stream crashed?
A: algom-poll executes scheduled, finite polling passes that exit cleanly regardless of payload status, while algom-stream attempts to maintain a continuous, stateful socket connection without sufficient error-catching on disconnects.
