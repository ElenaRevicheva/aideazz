The Gap Between Streaming and Polling

The contrast between algom-stream and algom-poll reveals the fundamental danger of streaming architectures. Both services handle data feeds, but their execution models handle network volatility differently.

algom-poll executes on a discrete schedule using node-cron. It wakes up, opens a connection, pulls records, closes the socket, and returns to sleep. If a connection drops midway, the cron job catches the error, records the failure, and terminates normally. PM2 sees a clean process exit code or an idle loop waiting for the next cron trigger, so the supervisor records 0 restarts over 7 days.

algom-stream, by contrast, maintains a persistent long-lived connection. When an upstream WebSocket drops or the remote socket is abruptly severed, an unhandled exception inside the listener crashes the Node.js runtime. PM2 catches the sudden process exit and immediately restarts the script.

Because the upstream provider was either rejecting the connection or timing out, the process crashed on initialization, entered restart backoff, and looped repeatedly until it racked up 21426 restarts. PM2 finally placed the process into a temporary pause: the waiting restart state. In this state, PM2 deliberate delays the next spawn to prevent total CPU lockup.

A stream crashes 21426 times if it lacks an exponential backoff wrapper inside application code. Handing connection retries entirely to a process supervisor like PM2 causes the supervisor to spin up new OS processes until rate limits or backoff delays choke the service.

Building Resilient Architecture Against Loop Failures

When a single process accumulates 21426 restarts, it highlights an architectural truth: supervision is not recovery. Relying on PM2 to keep an unstable socket alive causes resource waste and pollutes diagnostic logs.

To stop a service like algom-stream from entering waiting restart, the application layer must own the retry logic.

First, implement an internal backoff before letting Node.js exit. If a streaming socket drops, the client should sleep using an explicit backoff interval rather than throwing an uncaught exception. When the application traps errors internally, PM2 keeps the process in an online state, avoiding runaway restart counters.

Second, decouple message consumption from streaming connections. If the connection fails, data processing must halt gracefully while alerting the operations dashboard, rather than attempting hundreds of connection attempts per minute.

Frequently Asked Questions

Q: Why does PM2 show status "waiting restart" instead of "errored" or "stopped"?
A: PM2 places a process into waiting restart when it exceeds the restart threshold within a short time window. The supervisor applies an automated delay before attempting another spawn to prevent complete CPU starvation.

Q: How does algom-poll avoid the crash loops affecting algom-stream?
A: algom-poll uses discrete polling on a schedule via node-cron, closing its network socket after each run and reporting 0 restarts over 7 days. algom-stream maintains a persistent socket, which crashes the entire runtime when unhandled network drops occur.

Q: What caused the 429 errors recorded in hs-watch-manual-emails.log?
A: The script exceeded HubSpot's TEN_SECONDLY_ROLLING rate limit policy under group publicapi:private_app-api-calls-ten-secondly:39045903:51409153. The application caught the 429 status code and backed off rather than crashing the worker.

Q: How do disconnected AI coding agents collaborate on the cto-aipa repository without direct chat?
