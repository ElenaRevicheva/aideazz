Token-Bucket Throttling to Tame the Ten-Secondly Window

To eliminate synchronization drops, API requests cannot run concurrently in uncontrolled loops. Implementing a client-side token-bucket throttle ensures calls stay below the policy thresholds.

The token bucket mechanism works on two parameters:
1. Capacity: The maximum burst of request tokens allowed at any single instant.
2. Refill Rate: Tokens added back into the bucket over time.

When querying HubSpot deal properties:

  • Every outbound call must request a token from the bucket before issuing node-fetch or an HTTP request via httpx.

  • If the bucket has no available tokens, the execution thread yields execution using an asynchronous sleep timer rather than dropping the payload.

  • When an unexpected 429 response occurs, the runner catches the RATE_LIMIT error type, captures the correlation ID, and pauses execution across the polling worker instead of terminating the process.

This design shields scripts like reply-radar.log (which scanned 163 records with 0 errors) and espaluz-truth.log (which recorded 59 rows to truth_people) from cascading API blocks caused by runaway deal polling.
