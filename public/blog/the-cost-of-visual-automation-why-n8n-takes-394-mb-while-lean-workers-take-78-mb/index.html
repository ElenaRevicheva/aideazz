The Cost of Visual Automation: Why n8n Takes 394 MB While Lean Workers Take 78 MB

November 26, 2026 · by Elena Revicheva

n8n is running at 394 MB of memory on my production host right now, making it the heaviest single process across my entire server. In the exact same supervised fleet, algom-poll sits at 78 MB, pm2-logrotate uses 78 MB, and dragontrade-dashboard consumes 76 MB. If you operate automation infrastructure without VC backing on lean cloud instances, memory is not an abstract metric—it dictates how many processes survive before the kernel intervenes.

Here is the real breakdown of what production orchestration platforms consume in RAM versus supervised task scripts, drawn directly from live production metrics.

The Production Process Memory Footprint

My production workloads run on Oracle Cloud infrastructure supervised under PM2. Running pm2 jlist reveals exactly where RAM goes across 8 online processes out of 9 total workers:

  • n8n: online, 0 restarts, 394 MB
  • cto-aipa: online, 6 restarts, 208 MB
  • dragontrade-main: online, 0 restarts, 184 MB
  • serpapi-jobs: online, 0 restarts, 102 MB
  • whitespace: online, 0 restarts, 92 MB
  • algom-poll: online, 0 restarts, 78 MB
  • pm2-logrotate: online, 0 restarts, 78 MB
  • dragontrade-dashboard: online, 0 restarts, 76 MB
  • algom-stream: waiting restart, 1503 restarts

The visual workflow engine requires 394 MB simply to maintain its runtime graph, internal state, and active integrations. Meanwhile, specialized TypeScript and Node.js tasks doing focused work—like whitespace at 92 MB or serpapi-jobs at 102 MB—operate at a fraction of that memory. Visual convenience carries an architectural cost in the execution engine.

Why Visual Low-Code Engines Hoard Process Memory

Low-code platforms are built to handle dynamic node execution, state retention, visual canvas rendering data, and broad module compatibility. To provide an interface where non-programmers can drag blocks, the underlying runtime must load extensive schemas, routing engines, and persistent dependencies into memory.

When n8n runs, it does not merely execute a task and free memory; it maintains the execution tree, connection pools, and runtime state in heap. That is why it sits steadily at 394 MB while showing 0 restarts. It is stable, but heavy.

Compare this to specialized automation services. A dedicated background script like algom-poll performs its polling routine and sits idle at 78 MB. The difference comes down to execution overhead:
1. Dynamic typing and metadata verification across arbitrary visual nodes.
2. In-memory execution histories for debugging inside the user interface.
3. Heavy generic libraries loaded upfront to support possible node operations.

When you manage your infrastructure under strict resource constraints, deploying multiple low-code workflow runners quickly exhausts the instance capacity.

The Supervised Task Runner Alternative

To keep memory bloat under control, the majority of our automation runs as focused Node.js and TypeScript services or isolated CLI jobs instead of continuous low-code graphs.

For instance, looking at git commit activity in cto-aipa, we logged 12 commits over the last 48 hours refining direct bot behaviors. In commit fbaf3d21, we implemented channel learning from a forwarded post and ensured pending drafts persist on disk across restarts. In commit 7988af79 and commit ff00870c, we handled edge cases where an edit teaches the channel directly when forward actions are blocked.

Because these workers are purpose-built codebases using grammy or express, their memory profiles remain predictable: cto-aipa runs at 208 MB even with 6 restarts recorded, while dedicated dashboard interfaces like dragontrade-dashboard take only 76 MB.

Log files across our task fleet show this lightweight pattern in action:

  • cita-sort.log: executed sorting runs repositioning 0 cards across 3 boards cleanly.

  • concierge-selftest.log: completed 5 checks with 4572ms to the first card, confirming duplicate suppression and delivery.

  • espaluz-truth.log: wrote 478 rows to truth_people without accumulating process memory bloat.

By isolating tasks into scripts supervised by PM2 or periodic execution runners, you eliminate the constant 394 MB baseline tax imposed by heavy workflow engines.

When Visual Workflows Justify Their Memory Overhead

Visual automation platforms have a place, provided you account for their real footprint. We keep n8n online at 394 MB because it serves specific integration tasks where immediate visual feedback or rapid webhook adjustments are required.

However, running core high-frequency loops through a visual builder is an operational mistake if your hosting envelope is bounded. When a background loop crashes repeatedly—such as algom-stream logging 1503 restarts and entering a waiting restart state—diagnosing memory and connection leaks in a visual orchestrator is significantly harder than reading plain Node.js or Python logs. In our logs, Python background operations like model-tier.log clearly expose lower-level failures such as imaplib.IMAP4.abort: socket error: EOF, allowing direct remediation without traversing abstraction layers.

Use workflow automation platforms for low-frequency coordination between SaaS platforms, but keep heavy data pipelines and scheduled polling operations inside lightweight, supervised Node.js workers.

Frequently Asked Questions

Q: Can you reduce the 394 MB baseline memory of n8n on a small server?
A: You can tune queue modes or offload executions, but the idle memory floor of the service in our production environment stays measured at 394 MB under standard PM2 supervision.

Q: Why does algom-poll consume only 78 MB compared to cto-aipa at 208 MB?
A: algom-poll runs a single, focused polling task with minimal active dependencies, whereas cto-aipa handles interactive Telegram bot logic, draft persistence, and API routing, which pushes its heap to 208 MB across 6 restarts.

Q: Does restarting a process clear Node.js memory accumulation permanently?
A: Restarting resets heap usage temporarily, but if the underlying architecture loads extensive dynamic dependencies—as visual engines do—the process will return quickly to its operating baseline.
