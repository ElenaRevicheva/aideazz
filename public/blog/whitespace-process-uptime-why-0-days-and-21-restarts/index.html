Whitespace Process Uptime: Why 0 Days and 21 Restarts?

October 22, 2026 · by Elena Revicheva

The whitespace process shows 0 days uptime and 21 restarts. This is a fresh deployment, yet it already has a restart count. Other processes like algom-poll and n8n have 0 restarts and up 86 days and 70 days respectively. The dragontrade-dashboard is up 67 days with only 1 restart. This discrepancy immediately signals a problem: a new process should not be restarting at all, let alone 21 times, on its first day.

The Anomaly of whitespace

My pm2 jlist output shows whitespace as online, consuming 114 MB of memory, but with an uptime of 0d and 21 restarts. This is a critical indicator. A process that has been restarted 21 times on the same day it was deployed is not stable. For comparison, cto-aipa has 223 restarts but has been up for 1 day, implying those restarts happened over a longer period, or in bursts. algom-stream has 55193 restarts but has been up 67 days, which is a known issue I've addressed in other contexts. The whitespace process, however, is failing to maintain stability from the outset.

The whitespace process is related to the Atlas/WHITESPACE shells, which provide "free daily scans across all of Latin America + Spain + US". This functionality is critical for our lead generation and market intelligence. A commit in aideazz on 2026-10-21, f5e552d, specifically mentions "Atlas/WHITESPACE shells: free daily scans across all of Latin America + Spain + US (regenerated from the app's faqData)". This suggests recent deployment or modification.

Investigating Recent Deployments and Commits

The aideazz repository, where the whitespace process's related code likely resides, shows 7 commits in the last 48 hours. The f5e552d commit on 2026-10-21 is directly related to WHITESPACE functionality. This timing aligns with the 0d uptime observed for the whitespace process. It's highly probable that the restarts are a direct consequence of this recent deployment or the code changes introduced.

While the cto-aipa repository also saw 12 commits in the last 48 hours, these were focused on "Pitz deep dive" and "Deals sheet merges", as seen in commits like 3b2cddc5 and 6d7ca384 on 2026-10-22. These changes are unlikely to directly affect the whitespace process. The aideazz commits, however, are directly relevant.

The Impact of whitespace Instability

The whitespace process is designed to provide "free daily scans". If it's restarting 21 times in less than a day, it's not reliably performing these scans. This directly impacts the data quality for deals. Addressing whitespace Process Uptime Reset

The immediate action is to review the code changes introduced by commit f5e5e52d and any subsequent aideazz commits that might affect whitespace. The whitespace process uptime reset to 0 days with 21 restarts indicates a fundamental issue, likely an unhandled exception or a configuration error that causes the process to crash and PM2 to restart it.

My approach would be to:
1. Examine whitespace logs: While not explicitly provided in the pm2 jlist output, PM2 manages logs for each process. I need to check the specific logs for whitespace to identify the exact error messages or crash reasons.
2. Rollback or hotfix: If the logs point to a clear error introduced by the recent f5e5e52d commit, a rollback to the previous stable version or a targeted hotfix is necessary.
3. Resource monitoring: Although 114 MB memory usage is not excessive, I would monitor memory and CPU usage more closely for whitespace to rule out resource exhaustion as a cause for restarts.

The goal is to achieve stability comparable to algom-poll (up 86 days, 0 restarts) or n8n (up 70 days, 0 restarts). A whitespace process uptime reset to 0 days with 21 restarts is unacceptable for a production system, especially one responsible for critical data acquisition.
